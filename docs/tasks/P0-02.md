# P0-02: Config loaders with validation
Phase: 0   Owner: GPT1   Card by: GPT2   Backlog: [P0-02, F04](../BACKLOG.md)

## Goal
Load `config/marketplaces.yaml`, `config/policy.yaml` and `config/checks.yaml` through Zod schemas so no rule or limit is ever hard-coded.

## Acceptance criteria
1. The three committed files load and validate.
2. A missing required field, a wrong type, or an unknown marketplace key fails with a message naming the file and field (one test each).
3. A profile whose `effective_date` is older than `recheck_after_days` is reported as stale (test with a fixed clock).
4. Values marked `unverified` are surfaced as unverified, not treated as true.
5. A test fails if any marketplace limit number appears hard-coded in `src/` outside the schema defaults (simple grep test).

## Failure cases that must be handled
Each invalid input must fail with the file and field in the error. Cover missing fields, wrong types and an unknown marketplace key separately so each failure is visible.

## Out of scope / do not touch
Config values (GPT2 owns them via P0-05), marketplace research, the preflight runner and UI integration.

## Dependencies and assumptions
P0-01 must be merged. Use the three committed YAML files and the Zod stack specified in PLAN §6. D-009 keeps the loader portable. D-022 governs UTC dates. Document any new direct dependency with its exact version, licence, maintenance and a lighter alternative.

## Test approach
Write the Vitest tests first. Use the committed files for the successful load, fictional YAML in `tests/fixtures/config/` for validation failures, and a fixed clock for the staleness test. Include an `unverified` case and the source scan from criterion 5 in `npm run check`.

## Risks and stop condition
Fixture edits can hide a mismatch with the committed files. Keep the successful case on the committed inputs. Stop if validation would require changing a committed config value or safety rule, or if a dependency licence needs Ashley’s decision. Record the decision under Needs Ashley.
